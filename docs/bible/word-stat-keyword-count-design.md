# 관리자 단어 통계 — 키워드 직접 집계

## 구현 상태

**구현 완료(2026-08-30) / 운영 확인 전.** 단위 테스트 9건 통과. 실제 본문으로 돌려 본 적은
아직 없다.

| 구성 요소 | 위치 |
|---|---|
| 문자열 집계기 | `bible/application/component/BibleWordOccurrenceCounter.kt` |
| 저장 출처 | `BibleWordStatSource.KEYWORD` — 재계산 제외 대상 |
| 매처가 셀 수 있는 표제어인지 판별 | `BibleWordMatcher.isCountableTerm` |
| 미리보기 · 저장 | `AdminBibleWordStatService.countKeyword` / `saveKeywordStat` |
| API | `GET`·`POST /api/v1/admin/bible/word-stats/keyword` |
| 절 번호까지 뽑는 본문 조회 | `BibleVerseRepository.findVerseTextsByBook` |
| 화면 | `templates/admin/bible/admin-bible-word-stat-list.html` 의 `키워드로 집계` 패널 |
| 단위 테스트 | `BibleWordOccurrenceCounterTest` (9건), `BibleWordMatcherTest` (셀 수 있는지 판별 3건) |

- 상위 설계: [word-frequency-design.md](word-frequency-design.md)

## 1. 목표

관리자가 번역본과 키워드를 고른 뒤 `통계` 버튼을 누르면, 실제 본문에서 그 단어가 몇 번
나오는지 집계해 화면에 보여 주고 **같은 값을 `bible_word_stat` 에도 남긴다.**

**책은 고르지 않아도 된다.** 비우면 번역본 전체를 센다(§2.1).

화면에서 결과만 확인하고 끝나는 조회 기능이 아니다. 저장까지가 이 기능의 범위다.

예: 번역본 `개역개정` · 책 `창세기` · 키워드 `하나님` → `[통계]`

## 2. 동작 흐름

```
번역본 선택 → (책 선택은 선택 사항) → 키워드 입력 → [집계 후 저장] 클릭
  → bible_verse 본문 집계 → bible_word_stat 저장 → 결과 + 잡힌 절 표시
  → (아니다 싶으면) [되돌리기]
```

**한 번의 클릭으로 세고 저장한다.** 처음에는 계산과 저장을 두 단계로 나눴다 — 문자열 기준이라
결과를 보기 전에는 오검출인지 알 수 없어서다. 그런데 매번 두 번 누르는 것이 실제로 번거로워,
확인을 저장 뒤로 옮기고 **같은 범위를 통째로 걷어 내는 `되돌리기`** 를 결과 옆에 두었다.
오검출을 사람이 봐야 한다는 §3.2 의 요구는 그대로다. 보는 시점만 바뀌었다.

세어만 보고 싶을 때를 위해 `미리보기` 는 남겨 두었다(`GET`, 쓰지 않는다).

### 2.1 범위 — 책 하나 또는 번역본 전체

| 조회 폼의 책 | 세는 범위 | 결과 | 저장 |
|---|---|---|---|
| 고름 | 그 책 | 장별 횟수 | 그 책의 장 행 + 책 행 |
| 비움 | 번역본이 가진 책 전부 | **책별** 횟수 | 책마다 장 행 + 책 행 |

번역본 전체일 때 장별 값을 화면에 늘어놓지 않는 것은 장이 1,000개를 넘기 때문이다. 저장은
장 행까지 그대로 만든다 — 사용자 화면이 장 단위로도 읽는다.

**서버가 책을 순회한다.** 책 단위 재계산은 그러지 않는데(클라이언트가 책마다 호출한다), 무게가
다르기 때문이다. 재계산은 어휘 수천 개를 모든 어절에 맞춰 보고 15만 행을 쓰지만, 이쪽은 키워드
하나를 문자열로 훑고 많아야 천여 행을 쓴다. 미매칭 후보 리포트가 이미 같은 방식으로 번역본
전체를 훑는다(`findCandidates(bookOrder = null)`).

교체 범위도 요청 범위를 따른다. 책 하나를 다시 셌는데 다른 책 값까지 지우면 관리자는 무엇이
사라졌는지 알 길이 없다.

## 3. 집계 기준 — 문자열 등장 횟수

**본문에 그 문자열이 나온 횟수를 센다.** 어절을 정규화해 표제어에 매칭하는 기존 재계산과는
다른 방식이며, 그렇게 하기로 정했다(2026-08-30).

- 한 절에 3번 나오면 3회다.
- 책 전체와 장별을 모두 산출한다.

  | 범위 | 결과 |
  |---|---|
  | 창세기 전체 | 00회 |
  | 1장 | 00회 |
  | 2장 | 00회 |
  | … | … |
  | 50장 | 00회 |

- 산출한 책 합계와 장별 값이 그대로 `bible_word_stat` 에 반영되어야 한다.

### 3.1 이 선택으로 얻는 것

- **공백이 든 표제어.** `하나님 나라` 처럼 두 어절짜리 표제어 17건은 어절 하나씩 해시로
  조회하는 구조에서 영원히 0행이다(word-frequency-design.md). 문자열로 세면 값이 나온다.
- **중국어 번역본.** 토크나이저의 `NON_ALPHA`(`[^a-záéíóúüñç\s]`)가 한자를 통째로 지워서
  CUVT·CUVS 는 통계가 아예 만들어지지 않는다(`BibleTranslationType` 주석). 문자열 카운트는
  형태소 분석기 없이 이 번역본을 덮는 유일한 방법이다.

**"절의 수가 아니라 총 횟수" 는 여기서 얻는 것이 아니다.** `BibleWordMatcher.countBook` 은 이미
어절마다 1 씩 더하므로 기존 재계산도 총 횟수를 센다. 두 방식의 차이는 **무엇을 하나로 세느냐**
이지 절이냐 횟수냐가 아니다.

### 3.2 그래서 같이 지켜야 하는 것

문자열 비교는 형태소 경계를 보지 못한다. `말` 은 `말씀`·`말미암아` 를 전부 먹고, `물` 은
`물고기`·`재물`·`선물` 을 먹는다. 어절 단위인 매처에는 없던 오류다. 게다가 §4.1 의 자동 등록이
붙어 있어 **오검출 값이 새 표제어와 함께 사용자 화면으로 바로 나간다.** 2026-08-24 롤백과 같은
경로다.

- **관리자가 잡힌 절을 눈으로 본다.** 저장 결과에 실제로 잡힌 절을 함께 보여 주고, 아니면
  `되돌리기` 로 그 범위의 `KEYWORD` 행을 한 번에 지운다(§2). 되돌리기는 저장 뒤에 손으로
  고친 행(`MANUAL`)과 자동 등록된 표제어는 건드리지 않는다.
- **짧은 키워드는 경고한다.** 1~2자 한국어 키워드는 오검출이 사실상 확정이다(검색 키워드 집계도
  2자 미만은 제외한다 — search-keyword-ranking-design.md).
- **별칭도 함께 센다.** 매처는 별칭을 표제어 id 로 접어서 세므로(`BibleWordMatcher.buildIndex`),
  키워드 하나만 세면 같은 표제어 행에 재계산보다 작은 값이 들어간다.
- **`BLOCKED` 표제어는 계산도 거절한다.** 매처의 억제 집합이 하던 판단이 문자열 카운트에는
  없다. §4.1 의 등록 거절과 같은 이유다.
- **겹치는 매치는 세지 않는다.** 찾은 자리에서 키워드 길이만큼 건너뛴다.
- **비교 범위를 정한다.** 라틴 문자권은 소문자로 맞춘다(매처의 `matchKey` 와 같다). 한국어는
  본문을 그대로 본다 — 매처와 달리 구두점을 지우지 않으므로, 공백이 든 키워드는 줄바꿈이나
  중간 구두점이 끼면 맞지 않는다.

## 4. 기존 저장 정책과의 정합

`bible_word_stat` 에는 이미 `source`(`BibleWordStatSource`) 정책이 있다.

- 재계산(`POST /api/v1/admin/bible/word-stats/recalculate`)은 **책 단위**로 `AUTO` 행만 지우고
  다시 넣는다. `AUTO` 가 아닌 행은 그대로 살아남고, 그 (장, 표제어) 자리에 새 AUTO 행을 넣지도
  않는다.
- 책 행은 `chapterNumber = 0` 이고, 장 행의 **최종값**(MANUAL 포함) 합이다.

이번 기능은 다음과 같이 정했다.

- **저장 출처는 언제나 `KEYWORD` 다. 재계산이 이 행을 건드리지 않는다**(§6). 매처가 셀 수 있는
  단어라도 마찬가지다 — 계산 방식이 달라, 재계산이 덮으면 관리자가 잡힌 절까지 확인하고 저장한
  값이 조용히 다른 수로 바뀐다. 자동값으로 돌리려면 목록에서 그 행을 지운다(`자동값으로`).
- **저장은 그 표제어의 그 책 행을 source 를 가리지 않고 교체한다.** §4 앞머리의 "재계산이
  `MANUAL` 을 보존한다" 는 책 전체를 한 번에 다시 쓰는 동작에 대한 규칙이고, 여기서는
  관리자가 그 단어 하나를 콕 집어 다시 세라고 지시한 상황이다. 옛 값을 남기면 같은 단어의
  장 행과 책 행이 서로 다른 계산에서 나온 값으로 섞인다. 몇 행이 바뀌었는지는 결과에 적는다.
- 같은 (번역본, 책, 장, 표제어) 조합에 중복 행이 생기지 않는다. 교체가 곧 중복 방지다
  (지우고 넣는 사이에 `flush` 를 끼운다 — Hibernate 는 INSERT 를 DELETE 보다 먼저 내보낸다).
- 장별 값과 함께 책 행(`chapterNumber = 0`)도 그 자리에서 다시 쓴다. 재계산을 기다리지 않는다.
- 입력한 키워드를 `bible_word` 표제어에 어떻게 연결할지 → **없으면 자동 등록**(§4.1)

### 4.1 표제어가 없으면 등록하고 저장한다

`bible_word_stat` 은 `bible_word_id` 를 참조하므로 **어휘에 없는 키워드는 그대로 저장할 수
없다.** 관리자가 어휘 화면을 먼저 다녀오게 하지 않고, 저장 시점에 한 번에 처리한다.

```
키워드 정규화 → 어휘 조회 → (없으면) bible_word 등록 → bible_word_stat 저장
```

관리자가 직접 친 단어가 한 번에 한 건씩 들어오는 경로라, 후보 705건을 검수 없이 밀어 넣어
통계를 망가뜨렸던 일괄 등록(word-frequency-design.md 의 2026-08-24 롤백)과는 성격이 다르다.
다만 자동으로 어휘가 늘어나는 만큼 아래는 지킨다.

- **정규화 키(`BibleWordTokenizer.matchKey`)로 조회한 뒤 없을 때만 등록한다.** 글자를 그대로
  비교하면 `하나님` 과 `하나님의` 가 따로 등록되어 같은 단어의 통계가 둘로 갈라진다.
- **어휘는 번역본별이다.** 조회도 등록도 화면의 `translationId` 로 한다.
- **이미 `BLOCKED` 인 표제어면 등록하지 않고 그대로 알린다.** 차단은 관리자가 내린 판단이고,
  자동 등록이 그것을 조용히 되돌려서는 안 된다.
- 새로 만드는 표제어는 **`APPROVED`** 다(`BibleWord.keywordOf`). 관리자가 결과를 눈으로 보고
  저장한 단어이고, `CANDIDATE` 로 넣으면 방금 계산한 값이 사용자 화면에 나오지 않아 왜 안
  보이는지 알 수 없다. 분류는 알 수 없으므로 `ETC` 다.
- **0 회인 키워드로는 표제어를 만들지 않는다.** 저장 자체를 400 으로 끊는다. 이 방어가 없으면
  오타 하나가 어휘에 영구히 남는다.
- **새로 등록했으면 결과에 그렇게 적는다.** 조용히 늘어나면 어휘 목록이 관리 밖에서 커진다.

## 5. 화면

기존 화면의 번역본·책·장 필터를 그대로 쓰고, 그 아래에 `키워드로 집계` 영역을 두었다.
**늘 펼쳐 둔다** — 이 화면에서 가장 자주 쓰는 입구라 한 번의 클릭을 앞에 두지 않는다.
접었다 펴는 패널은 가끔 쓰는 `수동 행 추가` 쪽만이다.

- 키워드는 관리자가 자유 문자열로 입력한다. `하나님` / `NKRV` / `창세기` 를 하드코딩하지
  않는다.
- `통계` 를 누르면 **총 횟수 · 장별 칩 · 잡힌 절 5개**가 뜬다. 잡힌 절이 오검출을 확인하는
  자리다.
- `저장` 은 계산에 성공하고 0 회가 아닐 때만 열린다. 키워드를 고치면 다시 잠긴다 — 화면에
  보이는 결과와 다른 단어가 저장되는 것을 막는다.
- 결과는 사람이 넣은 문자열이므로 `innerHTML` 로 붙이지 않는다.
- 관리자 목록 화면은 표와 카드 목록을 함께 갖춘다 ([frontend.md](../../.claude/rules/frontend.md)).

## 6. 수동 행 추가 폼은 어떻게 되는가

지금 화면의 `수동 행 추가` 는 **자동 매칭이 잡지 못한 표제어를 넣는 유일한 입구**다. 이 기능이
그 자리를 가져가면 폼은 지울 수 있다. 단 두 가지가 그렇게 정해졌을 때만이다.

1. ~~집계 기준~~ **정해졌다(§3).** 문자열 등장 횟수라 공백이 든 표제어도 값이 나온다.
2. ~~새로 넣는 행을 재계산이 지우지 않는다~~ **정해졌다.** 출처를 `KEYWORD` 로 새로 만들고
   재계산 대상에서 통째로 뺐다.

§3 을 문자열 기준으로 정한 순간 이 값은 **매처가 재현할 수 없는 값**이 되었다. 처음에는 매처가
셀 수 있는 단어만 `AUTO` 로 두어 재계산이 덮게 했지만, 그러면 같은 단어의 값이 재계산 한 번에
조용히 다른 수로 바뀐다 — 관리자가 잡힌 절까지 확인하고 저장한 값인데도. 그래서 **매처가 셀 수
있든 없든 전부 재계산에서 제외**한다.

### 6.1 재계산 제외를 어디서 지키는가

| 위치 | 무엇을 |
|---|---|
| `BibleWordStatSource.PRESERVED_ON_RECALCULATION` | 보존 대상 = **`AUTO` 를 뺀 나머지 전부**. 출처가 늘었을 때 목록에 넣는 것을 잊어도 지워지지 않는 쪽이 안전하다 |
| `recalculateBook` | 보존 행을 `findByTranslationIdAndBookOrderAndSourceIn` 으로 모으고, 그 (장, 표제어) 자리에는 AUTO 행을 넣지 않는다 |
| `deleteByBookAndSource(AUTO)` | 그대로. `KEYWORD` 행은 애초에 삭제 조건에 걸리지 않는다 |
| `buildBookRows` | 책 행 합계에 보존 행의 최종값을 넣는다. 빠뜨리면 장별 값과 책 행이 어긋난다 |
| `AdminBibleWordService.countManualStats` | 어휘 삭제 경고. **재계산이 되살리지 못하는 행**을 센다(`MANUAL` + `KEYWORD`) |
| 관리자 목록 화면 | `AUTO` 가 아닌 행에 `재계산 제외` 배지와 `자동값으로` 버튼 |

`bible_word_stat.source` 는 `VARCHAR(10)` 이고 CHECK 제약이 없어 **마이그레이션 스크립트는
필요 없다.** `db/schema/bible_word_stat.sql` 의 컬럼 주석만 갱신했다(스크립트는 멱등이라 다시
돌리면 주석이 반영된다).

**되돌리는 길은 열어 둔다.** 목록에서 그 행을 지우면(`자동값으로`) 다음 재계산이 매처 기준
`AUTO` 행으로 다시 채운다. 매처가 셀 수 없는 단어라면 다시 채워지지 않으므로, 화면은 두 경우의
안내 문구를 다르게 보여 준다(`matcherCountable`).

**남은 것은 폼 제거 여부뿐이다.** 실제 본문으로 돌려 보고 값이 맞는지 확인한 뒤에 판단한다.

**폼을 지워도 값 수정 경로는 남는다.** 없어지는 것은 "행 만들기"이지 "값 고치기"가 아니다. 표
안의 횟수 인라인 수정(`updateByAdmin` — 이때 `MANUAL` 로 바뀐다)과 `자동값으로 되돌리기` 는
계산 결과를 사람이 보정하는 유일한 경로이므로 그대로 둔다.

## 7. 완료 조건

사전 재계산 작업 없이, 번역본을 고르고 키워드를 입력한 뒤 `통계` 를 누르면(책은 선택 사항):

1. `bible_verse` 본문 기준으로 단어 출현 횟수를 계산한다.
2. 책 전체와 장별 값을 함께 산출한다. 책을 고르지 않았으면 책마다 그렇게 한다.
3. `bible_word_stat` 에 반영한다 (중복 없음, 출처 `KEYWORD`).
4. 결과와 실제로 잡힌 절을 보여 주고, 되돌릴 길을 함께 준다.

구현 전에 Bible 모듈의 Controller / Service / Repository 와 Thymeleaf 구조, 그리고 기존 통계
정책을 먼저 확인하고 **기존 아키텍처를 최대한 유지하는 방향**으로 만든다.
